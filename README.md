# Inception

## Description

Inception is a system administration project: it sets up a small web
infrastructure made of several services, each running in its own Docker
container, all orchestrated with Docker Compose inside a virtual machine.

The stack serves a WordPress website over HTTPS at `https://mobenais.42.fr`:

```
                 host (VM)                       docker network "inception"
 browser ──443/TLS──▶ ┌────────┐  FastCGI :9000  ┌───────────────────┐  SQL :3306  ┌─────────┐
                      │ nginx  │ ───────────────▶│ wordpress+php-fpm │ ───────────▶│ mariadb │
                      └────────┘                 └───────────────────┘             └─────────┘
                           │                             │                              │
                           └──────── wordpress_data ─────┘                        mariadb_data
                                 (/home/mobenais/data/wordpress)          (/home/mobenais/data/mariadb)
```

- **nginx** is the only entry point, listening on port 443 with TLSv1.2/TLSv1.3 only.
- **wordpress** runs WordPress with php-fpm (no web server inside).
- **mariadb** stores the WordPress database.
- Two named volumes persist the database and the website files.
- All containers talk to each other through a dedicated bridge network.

## Project description

### Use of Docker and sources included

Every image is built from a Dockerfile written for this project, starting from
`debian:bookworm` (the penultimate stable Debian release). No ready-made image
from Docker Hub is used.

```
.
├── Makefile                  # generates secrets/.env, builds and starts the stack
├── secrets/                  # generated by `make secrets`, ignored by git
└── srcs/
    ├── .env                  # generated by `make secrets`, ignored by git
    ├── docker-compose.yml
    └── requirements/
        ├── mariadb/   Dockerfile, conf/50-server.cnf, script.sh
        ├── nginx/     Dockerfile, conf.d/nginx.conf
        └── wordpress/ Dockerfile, script.sh
```

- **mariadb/script.sh** initialises the data directory on first start (root
  password, database, WordPress user), then `exec`s `mysqld` so it runs as PID 1.
- **wordpress/script.sh** waits for MariaDB, downloads and configures WordPress
  with WP-CLI on first start (admin user + a regular author user), then `exec`s
  `php-fpm8.2 -F` in the foreground.
- **nginx** generates a self-signed certificate at build time and runs
  `nginx -g "daemon off;"` in the foreground.

### Main design choices

- **Debian bookworm** as base image: well-known packages, `apt`, stable.
- **No infinite loops / `tail -f`**: each container's main process is the
  service itself, started with `exec` so it receives signals as PID 1.
- **Initialisation only once**: a marker file (`.initialized`) for MariaDB and
  the presence of `wp-config.php` for WordPress make restarts idempotent.
- **Generated credentials**: `make secrets` creates random passwords in
  `secrets/` and writes `srcs/.env`; nothing sensitive is committed.
- **`restart: unless-stopped`** so containers come back after a crash.

### Virtual Machines vs Docker

A virtual machine emulates a full computer with its own kernel on top of a
hypervisor: strong isolation, but heavy (GBs of disk, slow boot, dedicated RAM).
A Docker container shares the host kernel and isolates processes with
namespaces and cgroups: it starts in milliseconds, images are small and
layered, and one container runs one service. Here the VM provides the isolated
host, and Docker splits the services inside it.

### Secrets vs Environment Variables

Environment variables are easy to use but are visible through
`docker inspect`, `/proc/<pid>/environ` and are inherited by child processes.
Docker secrets are mounted as files in `/run/secrets/` (tmpfs) only in the
containers that declare them, and do not appear in the image or in
`docker inspect`. Non-sensitive configuration (database name, usernames,
domain) belongs in `.env`; passwords belong in secrets. In this project the
MariaDB passwords are read from `/run/secrets/db_password` and
`/run/secrets/db_root_password`.

### Docker Network vs Host Network

With `network: host` a container shares the host's network stack: no
isolation, every port it opens is exposed on the host. A user-defined bridge
network (`inception`) gives containers their own isolated network with
built-in DNS (containers reach each other by service name: `mariadb`,
`wordpress`), and only explicitly published ports (here `443`) are reachable
from outside.

### Docker Volumes vs Bind Mounts

A bind mount maps an arbitrary host path into a container; it depends on the
host's directory layout and permissions and is not managed by Docker. A named
volume is created and managed by Docker (`docker volume ls/inspect/rm`), is
portable between hosts and decoupled from the host filesystem layout. This
project uses named volumes (`mariadb_data`, `wordpress_data`) whose data is
stored under `/home/mobenais/data` on the host through the local driver
options.

## Instructions

### Prerequisites

- A Linux virtual machine with Docker Engine and the Docker Compose plugin.
- `make` and `bash`.
- `mobenais.42.fr` resolving to the VM:

  ```sh
  echo "127.0.0.1 mobenais.42.fr" | sudo tee -a /etc/hosts
  ```

### Run

```sh
make secrets   # generate secrets/ and srcs/.env (asks for configuration)
make build     # build the images and start the stack
```

Then open `https://mobenais.42.fr` (accept the self-signed certificate).

### Clean

```sh
make clean       # remove secrets/ and srcs/.env
make secret_re   # regenerate secrets/ and srcs/.env
```

See [USER_DOC.md](USER_DOC.md) for day-to-day usage and
[DEV_DOC.md](DEV_DOC.md) for development details.
